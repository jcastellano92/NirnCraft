Reading and estimates only: no builds, no game runs, no servers. Sources read: the NeoForge 26.3.0.90 sources jar and
the patched Minecraft sources jar (paths below are inside those jars); recorder dumps from the autotest instance's
`.minecraft/atlas-trace/*/trace.json` (57 dumps, 2026-10-25 19:36-21:17). Spike code is not kept.

## Spike 1: can a mod skip vanilla water/lava meshing without a mixin?

**Answer: no through any public API; yes with one reflection swap (no mixin).**

Why the public API fails (NeoForge 26.3.0.90):
- `SectionCompiler.compile` (client/renderer/chunk/SectionCompiler.java:92-96) asks `fluidModelSet.get(fluidState).customRenderer()`
  and skips `FluidRenderer.tesselate` when `CustomFluidRenderer.renderFluid(...)` returns true
  (`net.neoforged.neoforge.client.fluid.CustomFluidRenderer`). That is the exact hook we want, but it lives on the
  per-fluid `FluidModel` record (client/renderer/block/FluidModel.java:15-21, field `customRenderer`).
- Vanilla water/lava models are baked with `customRenderer == null` (`FluidStateModelSet.bake`, FluidStateModelSet.java:34-39).
- `RegisterFluidModelsEvent.register` (nf client/event/RegisterFluidModelsEvent.java:57) uses `putIfAbsent` and throws
  on a duplicate, so vanilla water/lava cannot be re-registered.
- `ClientHooks.gatherFluidModels` ends in `Map.copyOf(models)` (ClientHooks.java:1039): immutable.
- `ModelEvent.ModifyBakingResult` exposes `BakingResult` (block-state and item models only), not fluid models.
  `IClientFluidTypeExtensions` has fog, tint and overlay hooks only, nothing for meshing.

No-mixin route that should work (to prove in round 2):
- In `ModelEvent.BakingCompleted` (fires at the end of `ModelManager.apply`, ModelManager.java:312, after
  `fluidStateModelSet` is set at :307), read `modelManager.getFluidStateModelSet()`. Build a replacement
  `FluidStateModelSet(Map, FluidModel missing)` whose water/lava entries are copies of the vanilla `FluidModel`s with a
  `CustomFluidRenderer` that returns true when the getter is a `RenderSectionRegion` (the public 6-arg `FluidModel`
  record constructor takes `customRenderer`). Put it into `ModelManager.fluidStateModelSet` (private, non-final field)
  by reflection. `LevelRenderer.invalidateCompiledGeometry` (LevelRenderer.java:1224-1229) reads it when it builds the
  `SectionCompiler`, so the swap takes effect at the next world join or `allChanged`.
- Alternative: set the private `final` `modelByFluid` field of `FluidStateModelSet`. Prefer the non-final field:
  JEP 500 (final means final) is heading for a default-deny of final-field reflection.
- Other mods keep working: fluids registered by other mods are untouched (we copy the map entries as they are), and
  `DynamicFluidContainerModel` / `FluidContentsTint` read the same `FluidModel` materials.
- Risk: it reflects into one vanilla-private field, so it is not public API. It needs a switch and a re-check on every
  Minecraft update (same rule as the mixin exception). A mixin on `FluidRenderer#tesselate` HEAD (inventory §4 row 1)
  is the fallback if the field moves.

## Spike 2: empty-model trick, and what vanilla meshing costs

Read path (confirmed in 26.3 sources): `ModelBlockRenderer.tesselateBlock` (ModelBlockRenderer.java:52-57) calls
`model.collectParts(level, pos, state, random, parts)` and does nothing when `parts` is empty.
`DelegateBlockStateModel` (nf client/model/DelegateBlockStateModel.java:39-41) delegates the level-aware overload,
which is the one to override. All other callers pass `BlockAndTintGetter.EMPTY` (`BlockStateModelWrapper.java:31`,
`LevelRenderer.java:1084` breaking cracks), so an `instanceof RenderSectionRegion` test affects section meshing only.
VisGraph, the block-entity list and the compiled flag come from `isSolidRender` / `hasBlockEntity` in the same loop
(SectionCompiler.java:78-91), untouched. So entities, block entities, cracks, falling blocks and held items are
unaffected by construction (to be eyeballed in round 2). Wrap at lowest priority so it wraps other mods' replacement
models. Sodium/Embeddium pass their own slice, not a `RenderSectionRegion`, so they still mesh (and the near pass is
off there anyway).

Cost data we have (recorder, autotest instance, warm world, steady-state flight):
- `mc:renderFrame (vanilla + every mod)` on the render thread: 1.7-2.0 ms per frame, 6-7% of a 27-28 ms frame
  (dumps 20261025-205505 .. 211742). This is an upper bound for everything vanilla does on the render thread outside
  our zones (extract, entities, GUI, compile scheduling, uploads); the share that is section meshing is not separable.
- Cold load: the same zone is 150 ms/frame in the first ~30 frames, 25 ms/frame at ~300 frames, 14 ms at ~700 and 5 ms
  at ~950 (20261025-210926 .. 211049), decaying to 2 ms. Some of this is vanilla's synchronous nearby compiles; not
  attributable from this data.
- **Worker-thread section-compile time is not in the recorder at all** (lanes are render thread, GPU, atlas threads,
  unnamed `thread N`); vanilla's own zone "Compile Section" (SectionRenderDispatcher.java:468) is never bridged. So
  there is no measured CPU saving yet. Estimate only: ~0.3-1 ms CPU per section, ~600 sections entering the view ring
  per 16 blocks of travel, so roughly 5-10% of one core while sprint-flying, and several CPU-seconds for a full cold
  load at render distance 16. Not a GPU number, and it does not touch the far-field cost.
- Empty meshes also free the vanilla vertex buffers (VRAM) and the upload/draw work; unmeasured.
